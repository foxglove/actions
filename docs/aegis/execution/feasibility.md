# Attack Runner feasibility and implementation seams

Read-only evidence gathered 2026-09-25. The Strix source candidate is [`usestrix/strix@ae38fe70`](https://github.com/usestrix/strix/tree/ae38fe70cd0260555a2ac745ca585e16bf3d6c74); Foxglove app evidence is [`foxglove/app@1d3459dc`](https://github.com/foxglove/app/tree/1d3459dceb5c438db22f5877312e428a1668dba7). These pins describe inspected source, **not** a qualified runtime, deployed party app, provider access, or immutable Strix sandbox image. No Docker is available in this planning environment; no target or model calls were run. A source-level probe fetched six Strix files at that commit and asserted the CLI flags, telemetry toggle, update-check switch, Docker-network hook, native artifacts and after-response budget check; all assertions matched. It did not execute Strix.

## Selected build boundary

Implement one bounded GitHub Actions job with a small TypeScript CLI and a narrow Python Strix bridge in foxglove/actions. Use Strix OSS for assessment; its native finding dedupe is useful _within_ a run but never substitutes for product-level causal identity across runs or fix claims. Our code validates configuration, stages the private instruction file, invokes the bridge, normalizes its artifacts, plans and delivers Linear changes, writes a private report, and preserves a permanent action journal. The bridge uses pinned Strix `run_strix_scan`/session APIs rather than directly invoking the CLI, because direct CLI cleanup destroys the ephemeral Caido session before trusted exchange export. Existing Foxglove Temporal is real ([evidence](orchestration.md)); a dedicated attack worker would add deployment/identity/isolation without removing Linear's uncertain external writes. The release contract needs neither transparent browser resumption after death nor an automatic report-recovery service. Choose Actions now; reconsider Temporal only if a later contract requires durable continuation across workers.

Suggested files in actions: `src/attack-runner/{schema,ingest,normalize,match,plan,journal,linear,report,strix,auth,main}.ts`, `src/attack-runner/strix_bridge.py`, `src/attack-runner/__fixtures__`, and approved `.github/workflows/aegis-party-pentest.yml`. Keep `ingest` through `plan` pure; `strix`, `auth`, `journal`, `linear`, `report` are explicit side-effect adapters. `yarn attack-runner plan --input fixture.json --output plan.json` is the offline command contract: UTF-8 versioned JSON in, deterministic logical JSON out, nonzero exit and diagnostic for broken envelope, partial-failure status plus valid decisions for malformed independent items. `yarn attack-runner run --profile party.json` is the later trusted-runner entry point; neither command exists yet. Pin Node/TypeScript versions against current actions main before coding.

## Auth source and confirmed gap

At inspected Foxglove app source, [`/auth/magic-link`](https://github.com/foxglove/app/blob/1d3459dceb5c438db22f5877312e428a1668dba7/packages/api/src/routes/internal/auth/magic-link/index.ts) lines 87–130 issues a token and emails it; only `NODE_ENV=test` returns a Redis lookup `requestId`. [`MagicTokenService`](https://github.com/foxglove/app/blob/1d3459dceb5c438db22f5877312e428a1668dba7/packages/api/src/services/MagicTokenService.ts) has a 15-minute token and single-use redemption. [`acl.ts`](https://github.com/foxglove/app/blob/1d3459dceb5c438db22f5877312e428a1668dba7/packages/api/src/lib/acl.ts) lines 613–639 accepts the HttpOnly session cookie and touches a session; touch does not prove cookie extension or a browser preserved for an hour. **Selected live route:** a dedicated, approved test-account mailbox reader controlled by the trusted runner. App/auth owner must provide mailbox delivery/reader identity and demonstrate unattended retrieval at party; if no safe supported reader exists, an app-owned secure retrieval interface is an external dependency. Do not use test-only Redis or pretend a mint response contains the link.

Implement a `MailboxReader.waitForLink({recipient, issuedAfter, timeout, expectedHost})` adapter: it returns exactly one link from a message delivered after the mint request, validates recipient/host and freshness, and never logs body/link; timeout fails preflight. The mailbox service, API and credential grant are **not identifiable from app source**, so the app/auth owner must select the existing service and supply its documented read API before live Slice 3 coding. Bounded qualification: with an approved test mailbox, request two links in separate runs, show distinct single-use links each delivered and consumed within 15 minutes, and prove the test-only Redis path is absent at party. A provider-specific mailbox implementation is a named external input, not a generic fallback guessed in this plan.

## Pinned bridge and provenance protocol

[`run_strix_scan`](https://github.com/usestrix/strix/blob/ae38fe70cd0260555a2ac745ca585e16bf3d6c74/strix/core/runner.py) lines 182–207 takes `scan_id`, `image`, `max_budget_usd`, `mcp_connection_requests`, and `cleanup_on_exit`; lines 625–642 call cleanup only when that last flag is true. [`session_manager.create_or_reuse`](https://github.com/usestrix/strix/blob/ae38fe70cd0260555a2ac745ca585e16bf3d6c74/strix/runtime/session_manager.py) lines 258–368 caches the same sandbox and exposes a `caido_client` handle; [`CaidoBootstrapHandle.get`](https://github.com/usestrix/strix/blob/ae38fe70cd0260555a2ac745ca585e16bf3d6c74/strix/runtime/caido_handle.py) waits for proxy readiness. [`caido_api.py`](https://github.com/usestrix/strix/blob/ae38fe70cd0260555a2ac745ca585e16bf3d6c74/strix/tools/proxy/caido_api.py) has `list_requests_with_client` and `get_request_with_client` with raw request and response options. Strix's own [agent-browser skill](https://github.com/usestrix/strix/blob/ae38fe70cd0260555a2ac745ca585e16bf3d6c74/strix/skills/tooling/agent_browser.md) documents `open`, `snapshot` and `eval`, plus distinct browser sessions; its default session is shared. These are concrete seams, but no browser/session behavior has been executed here.

Use one long-lived bridge process and a private JSON-lines pipe to Node. `prepare(runId,imageDigest,targets)` calls `create_or_reuse(..., local_sources=[])`, awaits `caido_client.get()`, then uses `bundle['session'].exec('agent-browser','open','about:blank')` and `snapshot` to verify the default browser session is ready. It emits only `ready(runId)` after that. Node then issues the link and retrieves it from the approved test mailbox; a `link` message carries it on the private pipe. Bridge substitutes the single committed placeholder in a private file, initializes Strix `ReportState`, and calls `run_strix_scan(scan_config=..., scan_id=runId, image=imageDigest, max_budget_usd=100, cleanup_on_exit=False, mcp_connection_requests=[])`. On return or catchable interruption, it obtains `bundle['caido_client'].get()`, pages `list_requests_with_client`, fetches cited IDs with `get_request_with_client`, exports encrypted/private request/response traces, then calls `session_manager.cleanup(runId)` in `finally`. It also exports native findings, coverage, usage and stop status. The outer Node timer can hard-kill the process; that is an interrupted run with potentially unavailable final proxy evidence, never a clean negative.

Mirror the pinned [`cli.py` scan setup](https://github.com/usestrix/strix/blob/ae38fe70cd0260555a2ac745ca585e16bf3d6c74/strix/interface/cli.py) lines 86–106: `scan_config` has `scan_id=runId`, `targets` from validated URL targets, `user_instructions` from the private substituted copy, `run_name=runId`, `diff_scope={active:false}`, `scan_mode='deep'`, `non_interactive=true`, `local_sources=[]`, `workspace_files=[]`, `scope_mode='full'`, `diff_base=None`, `resume_instruction=''`. Initialize `ReportState(runId)`, call `set_scan_config` and `save_run_data`, then `set_global_report_state` before `run_strix_scan`. Set explicit `mcp_connection_requests=[]` so the engine does not load a user's `~/.strix/mcp-servers.json`. On completion read `run.json.status`/`llm_usage`, `coverage.json` and `vulnerabilities.json`; treat Strix exit/finding status as separate from product delivery status. This pinned internal API is version-specific, so the bridge spike asserts its signature and artifact fields before any live profile is enabled.

For confirmation, the trusted bridge records an ordered validation event from the prepared browser's `/v1/me` request and response. From the Caido raw request it computes a **run-local keyed digest** of the HttpOnly session cookie; from the response it records expected non-admin actor/party without credential bytes. It compares each cited proving request's cookie digest, actor/tenant relation and sequence against that event. A routine server-issued replacement cookie requires a fresh validation event for the same jar/starting identity. A higher-privilege token/cookie **causally obtained from the validated non-admin session** is an exploit transition and remains positive when the trace proves that link; it is not discarded because `/v1/me` later reports elevated privileges. An unattributed replacement, wrong starting identity, unknown response, uncaptured exchange or post-loss request stays candidate/incomplete. The bridge triggers browser-context `/v1/me` maintenance every 300 seconds and before a declared high-impact chain; the instruction directs agents to invoke the same check. If a chain lacks a fresh pre-chain validation event, the adapter cannot confirm it. Shell/plugin traffic that bypasses Caido is denied by the external egress boundary and cannot prove a finding. These rules make product evidence conservative without asserting Strix's own text is authoritative.

The **controlled integration gate** must show on a fake authenticated app that the prewarmed browser receives the link within 15 minutes, `run_strix_scan` reuses its jar, Caido captures baseline/exploit/rotation/loss requests, the bridge exports before cleanup, and periodic/pre-chain validation survives concurrent Strix browser commands. If default-browser contention or source API drift breaks that sequence, a small pinned bridge/Strix patch is required and live release remains blocked. A source-level seam is not a passed runtime gate.

Bounded bridge spike for Slice 3: build only the Python bridge against the pinned wheel/image and a local fake app with two actors, one forbidden operation, cookie rotation and forced revocation. Drive one browser request, one shell `curl`, and one available plugin/tool request; each actionable HTTP exchange must appear in Caido with request/response, run-local cookie digest, actor and sequence. Deliberately bypass proxy settings in shell, including direct access to an otherwise authorized fake host: the external sandbox boundary must deny the request, and no uncaptured effect may confirm. Induce session loss and a bridge crash; assert earlier proven positive survives, later effect is incomplete, and export/cleanup/failure status are explicit. If native Strix tooling cannot satisfy this without a source patch, record the exact patch surface and keep live Slice 3 blocked; do not ask an implementer to infer a hook from report prose.

## Candidate finding → product observation

The adapter parses `vulnerabilities.json` per item, stores its raw `id` as `rawFindingRef` and cites `http_exchange_ids`/private traces. It does not copy Strix's title/dedupe decision into product identity. Require evidence for: validated starting actor and tenant, logical surface, resource relation, violated control, ordered prerequisites, operation and observed effect. A Strix report that only says “HTTP 200 means IDOR” remains incomplete. A privilege escalation performed _from_ the validated non-admin session is positive; an effect from an anonymous/wrong starting identity or after session loss is not. Native `coverage.json` and `run.json` supply candidate coverage/stop/usage, not an absence claim. The pinned bridge above is the selected collector path; until its controlled qualification succeeds, findings can be archived privately but cannot auto-create confirmed tickets.

Worked synthetic case: run `R2` has Strix raw report `vuln-0001`, “cross-org export,” citing exchange `x9`. A trusted trace shows tenant A's validated developer session fetched tenant B's export after listing its ID; the response contains B's data. Canonical cause is `(party, export download, A developer→B resource, missing tenant ownership check, B export, confirmed read, list→download)`. Existing issue `EXP-17` with the same cause but different title, repository, model and generated export ID matches: decision `rediscovered`, `exploitId=EXP-17`, evidence/count key `(EXP-17,R2)`, no routine alert. If no issue matches, proposal is one new exploit/ticket; if both `EXP-17` and `EXP-22` plausibly match, outcome is `unresolved` with both candidates and no write. A separate share-token validation defect in the same raw report yields a second cause/observation with shared prerequisites; a single ownership bug spanning two services stays one.

## Durable delivery example

For new `EXP-17`, Actions serializes party dispatches. The trusted runner CAS-writes a pending create reservation and UUIDv4 issue ID `u1` into a permanent private GCS corpus journal; then calls Linear with `id=u1` and marker `AR:create:EXP-17`. Current [first-party Linear schema](https://raw.githubusercontent.com/linear/linear/689ccc1e905d97df14272621b96a8614c5d3c2cb/packages/sdk/src/schema.graphql) declares optional UUIDv4 IDs for `IssueCreateInput` and `CommentCreateInput`; this is a source-level interface, not proof of duplicate-POST idempotency. On an acknowledgment loss, read `u1` and marker. Exactly one externally confirmed issue makes journal `applied`; null/not-found is not proof of noncommit, so `uncertain` blocks **all new creates** and requires operator resolution. There is no lease expiry or second provisional key that can mint an equivalent issue meanwhile. The run evidence comment and count representation each have separate `(exploitId,runId,action)` keys and persisted UUIDv4/comment markers. A contradiction reopen/notification episode has `(exploitId,fixClaimId)` keys; two runs against the same claim each deliver their own evidence/count and alert once. GCS generation CAS detects journal update conflict but is not a fence on Linear, so it never licenses blind retry. Parse old issue count honestly; unknown history stays unknown.
