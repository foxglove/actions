# Attack Runner implementation review packet

**Status: planning review completed; ready for offline implementation and the controlled bridge spike. Full live execution readiness remains conditional.** The current PR is the revision for Claude's review; this document provides the implementation review checklist and outstanding findings.

## Evidence-backed boundaries the reviewer must enforce

1. **Use Strix for what it already does.** Pin Strix source/release and sandbox image, cite the exact `run_strix_scan` bridge arguments and native output locations, and assign Strix its browser/tool execution, scan progress, reporting and usage functions where verified. New `foxglove/actions` code should own the missing product contract: authorized scope, fresh party auth, stable exploit identity, independent evidence reconciliation, Linear delivery coordination, private storage, and workflow operation. Reject a duplicate custom agent/harness loop without an observed Strix gap.
2. **Treat the Linear journal as a safety protocol.** [Current first-party Linear SDK schema](https://raw.githubusercontent.com/linear/linear/689ccc1e905d97df14272621b96a8614c5d3c2cb/packages/sdk/src/schema.graphql) defines optional caller-supplied UUID v4 `IssueCreateInput.id` (lines 18380–18382) and `CommentCreateInput.id` (lines 5776–5778), enabling a persisted ID before a create and exact readback after an unknown acknowledgment. It does **not** document safe duplicate mutation retries or conditional `issueUpdate` by version/state (lines 26026–26037). [Official Linear docs](https://linear.app/developers/graphql) require checking GraphQL errors even on HTTP 200; [attachment docs](https://linear.app/developers/attachments) guarantee URL idempotency for attachment+issue, not for issue/comment creation. Review prewrite journal persistence, exact-ID readback, sticky `pending/uncertain` reservations, action-specific proof before marking applied, and no blind retry. A GCS compare-and-swap or renewable lease cannot fence a stale process from calling Linear. Use append-only evidence/count comments and a minimal same-issue lifecycle change; refresh explicit fix-claim evidence before reopening and read back afterward. Concurrent engineer edits or unmapped states become uncertain rather than triggering a blanket description/status rewrite. The absent Linear CAS is an external race to handle honestly, not a reason to build another issue tracker.
3. **Constrain autonomous harness traffic at an actual boundary.** Inventory every Strix browser, HTTP, shell, plugin and model call path. An allowlist in prompt text or wrapper URLs is insufficient. The chosen container/proxy/network policy must block unapproved party hosts, non-party destinations, loopback/private/metadata IPs, redirects and DNS rebinding for attack tools while allowing only separately approved provider/auth/delivery traffic. Negative egress tests must observe connection attempts at the boundary.
4. **Disable optional telemetry before launch.** [telemetry.md](telemetry.md) records the inspected Strix outbound paths. At the final pin, review a minimal child environment with `STRIX_TELEMETRY=0`, `STRIX_NO_UPDATE_CHECK=1`, `OPENAI_AGENTS_DISABLE_TRACING=1`, no `TRACELOOP_*`/`OTEL_*`/analytics exporters or Exa/Perplexity keys, and no cloud/viewer invocation. The Strix source's PostHog and Scarf senders are default-on. Verify no attempted analytics DNS/connection through startup, success, finding, error and shutdown; a denied request is still an attempted emission. Required model/provider, app, Linear and private GCS requests are distinct service traffic.
5. **Preserve the planner and evidence semantics.** Whole shared-envelope corruption blocks all ticket delivery; independently malformed findings are quarantined while valid positives proceed under partial failure. Identity follows evidence-backed causal transitions across repos/models/path revisions; independently actionable boundaries split, and ambiguous partial chains remain unresolved. Non-observation does not prove a fix or write to a resolved ticket. Per-run confirmation evidence/count and per-fix-claim notification/reopen state have distinct keys. The private summary reports actual, failed, uncertain and unattempted delivery separately, with revision-scoped evidence and no public finding details.
6. **Check operational gates against actual interfaces.** Party magic-link retrieval and session maintenance, Strix model identifier/cost/stop behavior, GCS run-prefix IAM and effective expiry, Cloudflare attribution, Linear team/status/labels/fix-claim representation, and hosted workflow scheduling must each have a concrete owner, command/API shape, expected result and a live qualification gate. Do not infer success from fixtures or source declarations. Existing Foxglove Temporal worker and namespace patterns are credible alternatives; if Actions plus a small journal is selected, the packet must explain the bounded recovery scope and avoid recreating a workflow engine.

## Disposition on the reviewed plan

- **RR-01 — High, planning obligation resolved; runtime gate open:** The reviewed plan now specifies a narrow `run_strix_scan` Python bridge: prewarm the default browser and Caido, mint only after ready, export raw Caido exchanges before cleanup, derive a run-local keyed cookie digest from `/v1/me`, relate proving exchanges to actor/party and sequence, and quarantine uncaptured/unattributed/post-loss effects. It preserves causally proven escalation from the initial non-admin session. This is a conservative evidence rule, and the fake-app probe includes cookie rotation, a second actor, session loss, crash and deliberate direct-to-authorized-host proxy bypass. The actual browser jar reuse, concurrent maintenance, complete Caido capture and hard network denial remain **untested**. A proxy environment variable alone does not enforce egress. Until the controlled probe passes at the pinned image and final dependency lock, live auto-confirmation and ticket delivery remain blocked. [Pinned session API](https://github.com/usestrix/strix/blob/ae38fe70cd0260555a2ac745ca585e16bf3d6c74/strix/runtime/session_manager.py), [Caido API](https://github.com/usestrix/strix/blob/ae38fe70cd0260555a2ac745ca585e16bf3d6c74/strix/tools/proxy/caido_api.py).
- **RR-02 — High, planning obligation resolved; external race remains:** The reviewed plan persists caller UUIDv4 issue/comment IDs and markers before dispatch; only positive same-ID/marker readback marks applied. A null read after lost acknowledgment stays sticky-uncertain, stops automatic retry and blocks all new first creates until operator reconciliation. Per-run evidence/count and per-claim reopen/notification have distinct journal keys. The plan acknowledges that GCS CAS cannot fence Linear and calls for minimal same-issue lifecycle changes with pre/post readback; tests cover lost ACK and human-edit races. This is an implementable conservative protocol, not proof of atomicity. Before Slice 4 acceptance, inspect the **implemented** state mapping, explicit fix-claim refresh, comment/issue readback and mutation error handling against the actual Linear workspace; any ambiguous status or stale-owner edit remains uncertain. [First-party schema](https://raw.githubusercontent.com/linear/linear/689ccc1e905d97df14272621b96a8614c5d3c2cb/packages/sdk/src/schema.graphql), [GraphQL error guidance](https://linear.app/developers/graphql).
- **RR-03 — High, planned opt-out; runtime gate open:** The final plan sets `STRIX_TELEMETRY=0`, `STRIX_NO_UPDATE_CHECK=1` and `OPENAI_AGENTS_DISABLE_TRACING=1` in an allowlisted child environment before Python imports Strix. It separates target-app PostHog/Sentry and required provider/auth/Linear/GCS/GitHub service traffic from optional Strix analytics. The bridge bypasses CLI-only update/start hooks, but shared telemetry hooks and transitive dependencies still require a captured startup, finding, error and cancellation test. No zero-egress claim is established until the exact pinned lock/image passes that test; [telemetry.md](telemetry.md) is the inventory and oracle.

**Verdict: pass the plan for offline contract/planner implementation and the bounded bridge qualification spike; do not call the complete live runner execution-ready yet.** The source-backed bridge and conservative Linear algorithm remove the material prose/design unknowns. The remaining blockers are concrete external or runtime gates named in `feasibility.md`: immutable Strix image/dependency lock and bridge/egress capture proof, approved mailbox API and demonstrated 15-minute/full-run session route, exact allowed Sonnet-4-8 provider ID and effective per-run $100 cap, provisioned private GCS journal/sink IAM, actual Linear workspace mappings/readback, and observed no-analytics egress. None was executed in this review environment. Implementers can start pure slices and the controlled spike; live auth/assessment/delivery must wait for their respective gates. A failed bridge spike should identify a minimal pinned patch or dependency, not silently relax evidence rules.

These are review gates, not product-policy changes. No live Linear mutation, party request, Strix scan, GCS write, network capture or code test has been performed for this review.
