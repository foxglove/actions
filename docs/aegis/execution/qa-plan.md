### Additional release gates and negative oracles

- **Strix bridge lifecycle and output mapping:** On the pinned build, call the selected bridge against an inert local fixture with `run_strix_scan(cleanup_on_exit=False)`, then inspect the reused sandbox/Caido client, paginated `list_requests_with_client`/`get_request_with_client` raw request/response traces, `vulnerabilities.json`, `coverage.json`, `run.json`, events, status and partial files before explicit cleanup. Assert the `ready` record precedes link retrieval; the same private pipe then conveys the fake link, and the bridge's `finally` cleans `scan_id` only after evidence export. Inject normal completion, finding, no finding, budget stop, exception, cancellation and timeout. The bridge must export redacted evidence and a trace/cleanup result before cleanup; cleanup must run exactly once when execution still permits. Prove run-local keyed cookie digests plus `/v1/me` actor/party/sequence bind each actionable exchange without persisting raw cookies. An ordinary server rotation needs revalidation, while a trace-proven exploit-derived admin capability remains positive. A missing trace, failed export, stale pre-chain validation or invalid starting-session binding leaves a candidate unresolved, even when Strix labels it a validated vulnerability. A zero-finding report with interrupted auth, edge access or budget is incomplete coverage, not negative proof. Reuse Strix's scanning and within-run finding machinery; do not claim its native dedup establishes product identity across runs or its output alone proves the actor/session.
- **No optional telemetry:** At pinned Strix commit `ae38fe70cd0260555a2ac745ca585e16bf3d6c74`, `strix/config/settings.py` defaults telemetry on and `strix/telemetry/posthog.py` and `scarf.py` gate their sends with `STRIX_TELEMETRY=0`. The command-line launch control is an environment prefix such as `STRIX_TELEMETRY=0 <trusted-runner-command>`; the selected Python bridge must also see it **before Strix import** and propagate only approved variables to children. Add `STRIX_NO_UPDATE_CHECK=1` and `OPENAI_AGENTS_DISABLE_TRACING=1` before import, and strip inherited optional tracing/search/MCP keys as required by [telemetry.md](telemetry.md). In local inert success, forced-error, cancellation and timeout cases, compare absent variable (source default-on behavior) with explicit `0`, inject conflicting inherited environment/config values, and inspect bridge/child environment plus spy sinks for PostHog, Scarf, update, tracing, crash and dependency analytics. Include image/package installation and update steps in the inventory: a scan-process opt-out does not retroactively stop installation-time analytics. Source audit and spy tests establish only known code paths. Separately inspect qualified egress logs/network denies for whole-stack behavior; neither a successful local spy nor a prompt instruction proves zero live exfiltration. Required configured model-provider calls remain a separate permitted traffic class.
- **Target-app browser traffic:** Inspect the actual browser/proxy egress trace for the party app's own analytics and error-reporting calls as well as Strix-owned traffic. App source indicates PostHog-style event/identify and feature-flag traffic plus web Sentry initialization; `STRIX_TELEMETRY=0` does not disable those or app server-side audit/access logs. Record exact observed destinations/payload classes and the effect of any scoped block on feature flags or assessment coverage. Do not change global app analytics/feature-flag configuration as a test shortcut; if an analytics destination shares necessary feature-flag service behavior, qualify the scoped policy and coverage limitation with the app owner.
- **Scope and egress:** From every pinned Strix browser, HTTP/proxy, terminal and plugin network-capable tool, attempt only safe synthetic off-scope destinations under controlled isolation. Confirm deny at the actual network boundary for unapproved party host, off-domain, loopback/private/metadata IP, redirects and changed DNS, while necessary trusted runner/provider traffic remains separately routed. The presence of `STRIX_DOCKER_SANDBOX_NETWORK` alone does not pass.
- **Schedule/worker death:** Test nominal and delayed scheduled starts, DST, operator loss immediately before auth, and process death after positive but before summary. Never automatically restart a live pentest from a stale cookie or use an unverified Strix resume facility. The existing run retains observed delivery/evidence states where durable, and any later attempt is a separately identified run with fresh preflight.
- **External exactly-once boundary:** A private GCS compare-and-swap, local event log, or Strix native dedupe does not establish Linear applied state. The I-06 oracle requires external per-action proof or an explicit uncertain result with unsafe retry blocked.
