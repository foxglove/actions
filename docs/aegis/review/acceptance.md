# Attack Runner acceptance criteria

This is a draft verification plan, not a record of passing tests. It translates the product documents into observable implementation outcomes. Preserve criterion IDs when refining fixtures or test details. The [engineering handoff](engineering-handoff.md) describes implementation boundaries and unresolved technical dependencies.

**Review audience:** Automated reviewers are encouraged to review this document for contradictions with the product docs, missing edge cases, and criteria that cannot be verified objectively. Human review of this document is optional. Report substantive findings with the criterion ID and the behavior that would fail; do not require human sign-off merely because this is an acceptance document. Product decisions still belong in the product docs.

Non-observation never establishes absence or a fix, including when a targeted re-test completes. Keep observation, execution/coverage status, ticket lifecycle, and delivery status separate. The product documents contain the [run/session lifecycle](../../../product-docs/attack-runner.md#run-and-session-lifecycle), [ticket lifecycle](../../../product-docs/exploit-findings.md#ticket-lifecycle), and [finding reconciliation and delivery](../../../product-docs/exploit-findings.md#finding-reconciliation-and-delivery) diagrams.

### Private authentication handoff

These cases implement the [issuer boundary and handoff lifecycle](../../../product-docs/attack-sessions.md#issuance-and-handoff-lifecycle). They require runtime evidence before enabling the recurring service.

| ID   | Scenario                                                                                                                           | Required observable result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I-18 | Two clean scheduled runs; employee account removed in an isolated fixture                                                          | Each run bootstraps from company-owned identities and gets a distinct link/session without an employee cookie, mailbox or manual step. Deleting the fixture employee does not break bootstrap; operator coverage remains required.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| I-19 | Runner/harness attempts issuer or cross-run access                                                                                 | Runner has no superadmin or signing credentials and cannot impersonate the issuer, change its deployment/identity mapping/IAM, or select arbitrary targets. It can read only its assigned handoff, with no list/write/delete/admin or other-run access, including inherited grants. Runner can read only its own attempt’s redacted cleanup status; listing/cross-attempt reads and any status-record write/delete are denied, including inherited grants. Harness cannot obtain issuer or storage credentials through environment, files or metadata.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| I-20 | Duplicate readiness/delivery; stale, mismatched, cancelled or nearly expired handoff; crash/uncertain redemption                   | Authenticate run/attempt authorization and claim once. Duplicate events do not create parallel mint/redemption. Validate envelope, object generation, allowed URL, identity/profile/mode and minimum lifetime against trusted configuration. Invalid input starts no assessment. Read retries precede redemption only; uncertain redemption ends the attempt. Any restart is separately identified and bounded by original job limits.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| I-21 | Bootstrap stops before issuance; login succeeds; cancellation/expiry/crash; deletion or acknowledgment fails                       | Issuer-owned cleanup deletes only the expected generation and covers orphaned objects without runner cooperation. Verify no versioning, soft-delete recovery or retention lock in the transient bucket; evidence policy is unchanged. Cleanup retry limits/delay are explicit, issuer-owned per-attempt status/timestamp/reference shows confirmed deletion or explicit failure, including a late completion after summary publication. Derive the status reference before issuance; a bootstrap stop before any issuance request records unknown with the explicit pre-issuance stop reason and creates no issuer record/handoff. Summary preserves its observed pending/unknown snapshot and reference without claiming future cleanup; test the selected private failure destination and delivery failures before release. No credentials in outputs; prior valid findings survive cleanup failure. Application expiry remains effective independently of deletion; test single-use/concurrent redemption rather than treating storage read as consumption. |
| I-22 | Ordinary profile receives impersonation link labelled ordinary; actual-mode evidence missing/ambiguous; selected mode is qualified | Adapter verifies actual mode with qualified application-derived evidence after redemption, independently of the envelope label. Mislabelled, unapproved, mismatched or unknown mode fails preflight; attack tools stay gated until the adapter passes mode and identity checks. An approved mode records source and coverage limitations; actual member/org/non-admin role and full-duration maintenance are verified. No equivalence claimed from matching member alone. Later causally demonstrated privilege escalation from a valid starting identity remains positive evidence.                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

Soft-fail means the assessment is not a required merge gate. It does not mean reporting a failed assessment or failed delivery as successful.

## Evidence required at handoff

E1-16 is verified by the final-revision handoff check, not by a planner fixture. It applies to the delivered code and the evidence recorded for that revision.

| ID    | Scenario                                                 | Required observable result                                                                                                                                             |
| ----- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1-16 | Delivered code differs from earlier tested/reviewed code | Re-run affected checks and review the final revision. Record its commit or patch hash and matching command/results evidence; do not report earlier results as current. |

Record the evaluated commit, command, exit result, and evidence for each applicable case. Report failed, skipped, and untested cases explicitly. Integration criteria require controlled runtime evidence; a mock or a prompt assertion alone does not prove session lifetime, budget enforcement, or external delivery. No implementation or live validation has been performed in this documentation pass.
