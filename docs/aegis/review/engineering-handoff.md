# Attack Runner engineering handoff

This document translates the proposed product behavior into implementation boundaries, inputs/outputs, and evidence needed to ship. It is not a second product specification. Update the product documents when behavior changes; keep work status in implementation issues and PRs.

**Review audience:** Automated reviewers are encouraged to review this handoff and the [acceptance criteria](acceptance.md) as technical review targets. Check consistency, missing interfaces, failure/retry behavior, unproven assumptions, and gaps in verification. Human review of these two documents is optional. Raise a focused product question when a genuine decision is missing; routine implementation choices do not require a separate human approval gate.

## Product contract

Read [Attack runner](../../../product-docs/attack-runner.md), [Exploit findings](../../../product-docs/exploit-findings.md), [Attack sessions](../../../product-docs/attack-sessions.md), and [Attack paths](../../../product-docs/attack-paths.md), including their References. The [instructions file](../attacks/authenticated-access-chains/instructions.md) owns first-path mechanics. The product documents contain the [run/session lifecycle](../../../product-docs/attack-runner.md#run-and-session-lifecycle), [ticket lifecycle](../../../product-docs/exploit-findings.md#ticket-lifecycle), and [finding reconciliation and delivery](../../../product-docs/exploit-findings.md#finding-reconciliation-and-delivery) diagrams. The PR description provides proposal context, not the canonical behavioral contract.

Preserve these invariants in implementation:

- One complete ticket per independently actionable exploit, irrespective of repository; identity follows evidence-backed causal boundaries and transitions rather than wording.
- A non-observed exploit is not proven absent or fixed. Engineer-resolved tickets receive no writes for non-observation; only the run summary records coverage and stop reason.
- Confirmed contradiction of a fix claim reopens the same closed ticket with evidence. Unknown or failed delivery is not reported as successful.
- Count a confirmed exploit once per distinct run; replay does not increment it. Unknown historical counts stay unknown.
- Establish a fresh magic-link login immediately, then preserve the same cookie session with verified maintenance. Stop on session loss and retain completed evidence.
- The issuer function is company-owned. Attack Runner, including its controller, has no superadmin access, issuer impersonation/deployment authority or personal-authentication dependency. It reads the ordinary magic-link message from a dedicated company mailbox with read-only access to that one mailbox; the harness receives no issuer or mailbox-administration credential. The ordinary-login route requires no authentication; `security: []` is no required authentication, not external reachability, so issuer separation is operational, not a security boundary for issuance, when the route is reachable.
- Keep runtime settings interchangeable. Sonnet-4-8 is the selected assessment default; verify its provider identifier and pinned Strix support rather than silently substituting.
- Produce the summary and redacted evidence only in the private GCS destination; the trusted runner owns storage access, and the harness never receives those credentials. Slack delivery is deferred.
- Start scheduled runs Monday 09:00 America/Los_Angeles with an operator available to observe/stop them; skip visibly if coverage is unavailable.
- Distinguish edge blocks/challenges and unclassified access failures from application authentication/authorization results. Unreached targets have incomplete coverage, not a successful negative assessment.

## Recommended implementation sequence

Build a small deterministic offline planner first. It consumes synthetic run observations and existing-ticket snapshots and emits proposed actions, with no external writes. This makes identity, evidence, and lifecycle rules testable before integration. Investigate authentication and harness compatibility early so feasibility problems surface before substantial integration work. This is an implementation recommendation, not an intermediate product release.

Documentation review alone does not launch live assessments.

## Offline planner contract

Define the concrete input/output schema, entry point, and test fixtures before implementing the planner and adapters. They must implement the product decisions linked above. Specify which inputs are already normalized and which matching or normalization decisions the planner owns; do not hide untested identity decisions at an undocumented boundary.

Inputs describe one assessment run, normalized observations, relevant existing issue snapshots, explicit observation and execution/coverage results, and previously processed event identities. Required meaning includes:

- Run identity and evidence location; completion/session/coverage information sufficient to judge each observation.
- Exploit identity, target environment, affected surfaces, severity, and production-impact assessment; ordered activity-chain evidence, remediation, and fix-verification expectations. Affected repositories/components are optional metadata, not a required matching key.
- Existing issue identity and whether it is still open, explicitly claimed fixed, or unknown; a reference identifying the fix claim when applicable.
- Re-test target/identity, what was attempted and observed, execution/coverage status, and stop reason. Non-observation never asserts that the exploit is absent or fixed.
- Previously processed run/finding identities for replay handling.

Engineering documents one concrete JSON/API shape shared by the planner and its adapters. Vendor issue status strings must be mapped explicitly at the adapter boundary. The offline planner receives normalized states, not a guessed interpretation of a title or “Done” label.

Outputs contain a per-finding decision, reason, evidence references, target issue or new-issue proposal, and proposed evidence/counter/lifecycle changes and summary entries. Incomplete decisions contain a reason and needed evidence, with no misleading resolved/fixed action. Emit machine-readable results plus a short runnable example. The output is an action proposal, not proof of successful delivery.

| Evidence and issue state                                                    | Product outcome                    | Proposed action                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Valid confirmed positive; identity established; no match                    | new                                | Propose one exploit ticket with the full activity chain, remediation, and required evidence, regardless of affected repositories                                                                                                    |
| Valid confirmed positive; exactly one open match                            | rediscovered (still open)          | Append evidence and count this run once; no Slack event                                                                                                                                                                             |
| Valid confirmed positive; exactly one explicit fix claim                    | claimed-fixed but still reproduces | Append evidence, identify the claim, and propose reopening the same ticket if closed; no duplicate ticket                                                                                                                           |
| Run ends without observing a tracked exploit                                | not observed in this run           | Record attempts, conditions, coverage, evidence references, and stop reason in the run summary. A resolved ticket receives no comment, attachment, counter change, or lifecycle update; no absence/fixed claim or automatic closure |
| Invalid evidence, ambiguous identity, or unknown state required for a write | unresolved processing              | Explain the missing evidence; no speculative creation, merge, or lifecycle action. Interrupted coverage alone does not invalidate an independently confirmed positive                                                               |

A session lost after a completed positive observation does not erase that observation. Process independently valid evidence while marking unfinished coverage as interrupted. When no exploit was observed, retain that scoped observation separately from the execution status. Never translate overall run failure into “everything still exists” or “everything is fixed.”

Determinism means equal normalized input and prior-event state produce the same logical plan. Stable ordering is useful, but tests should assess semantic results rather than incidental field order. The planner is not required to provide distributed exactly-once delivery; Engineering 2 must persist deduplication state and coordinate actual writes.

## Operational qualification

### Authentication issuer and mailbox delivery

Every authentication product decision in [Attack sessions](../../../product-docs/attack-sessions.md#product-decisions) has a selected outcome, a named accountable owner, and accepted coverage limitations; only executable qualification work remains (this section and I-01, I-02, I-16, I-18–I-23). The named owners must accept operational ownership before live release.

Implement the [session contract and login diagram](../../../product-docs/attack-sessions.md#issuance-and-login-lifecycle). Ordinary non-admin login is the selected mode; see [Attack sessions](../../../product-docs/attack-sessions.md#product-decisions). The inspected ordinary magic-link route emails the link and returns success, not a raw token, and creates an ordinary session for a token without an impersonator claim. The superadmin impersonation path returns a link directly and creates an impersonation session; it is not selected, and a superadmin-generated link must not replace ordinary login. Qualify how the company issuer function reaches and is authorized to call the supported ordinary-login path; do not invent a new endpoint or assume the test-only retrieval shortcut is available on party. Mailbox provisioning and any app changes belong to their owning repositories and are separate dependencies of this actions change.

The inspected ordinary magic-link route requires no authentication: `packages/api/src/specs/internal.yaml` sets `security: []` on `/auth/magic-link`, which emails a link to any supplied address, rate-limited only. A caller that can reach the route can therefore trigger a link email to the mailbox. `security: []` establishes no required authentication, not external reachability. Where the route is externally reachable, the runner can call it itself, so issuer and runner separation is then an operational choice, not a security boundary for issuance. Verify that an unauthenticated external caller can reach `/auth/magic-link` on the party environment before relying on this, and treat the accepted denial-of-service risk and the operational-choice framing as conditional on that reachability. The enforced controls are the dedicated read-only mailbox, single-use and 15-minute expiry, the pre-redemption sender and URL checks, and post-redemption identity and mode verification.

Use distinct company-owned scheduler, issuer and runner authorities. The authorized run/attempt/profile determines the test identity on the issuer side. Authenticate readiness; it cannot change the identity. The mailbox is dedicated to the test identity and is used for no other purpose. The runner requires exactly one ordinary magic link for the approved identity delivered after its own readiness time, which it observes and which precedes issuance, so it needs no timestamp from the issuer; if no message or more than one message matches within the window, it fails preflight rather than guessing. The first release runs one weekly assessment with one active attempt, so a shared mailbox is not read by concurrent runs; a bounded restart is a new attempt within the original job limits. If the redemption outcome is uncertain, fail the attempt; the unredeemed link expires on its own.

Before redemption, validate the selected message against independently supplied configuration, not against values the message asserts. The adapter holds no signing key and cannot verify token claims before redemption, so name the trusted source for each check:

- Sender authenticity and mailbox binding: the runner reads through a mailbox API and cannot compute SPF, and does not trust an `Authentication-Results` header, which a sender can forge. The first release verifies the DKIM signature itself: `d=` equals the configured signing domain, matched without case; the `h=` tag covers `From`, `To`, `Subject`, and `Date`; the signed `From` header equals the configured application sender; the signed `To` header equals the company mailbox address from trusted configuration; and there is no `l=` tag. The configured signing domain is the domain that SendGrid signs with. It can be a subdomain, such as `em.foxglove.dev`, so the adapter does not require it to equal the `From` domain. A subdomain or a parent of the configured signing domain fails. A shared provider signing domain, such as `d=sendgrid.net`, is not accepted, because any customer of that provider can send under it. Other services can also hold a DKIM key for the configured domain, so the `s=` selector must be one of the configured SendGrid selectors. A valid signature with an unapproved selector is classified `DKIM_SELECTOR_UNAPPROVED`, distinct from a forged message, to prompt an investigation. The classification does not by itself show whether the selector is a legitimate SendGrid rotation or a different service, so the app/auth code owners confirm against the SendGrid domain-authentication settings before they add the selector to the configured selectors. DKIM does not sign the SMTP envelope recipient, so `d=` alignment alone does not prove delivery to this mailbox; the signed `To` binding rejects a genuine link that the application addressed to a different account and that a party replayed into this mailbox. A party can add an unsigned header above a signed one, and the signature stays valid. A DKIM verifier selects header fields from the bottom up. The adapter therefore rejects a message with more than one `From`, `To`, `Subject`, or `Date` header. It compares only the header instance the signature covers, by address for the mailbox and by the signed value for the date. A forged, unsigned, misaligned, replayed, or duplicate-header message fails preflight, and the runner does not open its URL. An unapproved-selector message also fails preflight, under the `DKIM_SELECTOR_UNAPPROVED` classification above, not as a forgery. Verify the application's signing `d=` domain, the `s=` selectors, the `h=` header list, and the absence of an `l=` tag against a genuine message; see the [Appendix](../../../product-docs/attack-sessions.md#appendix).
- Sign-in URL: the link host and path match the approved application sign-in URL from trusted configuration. The link URL itself comes from the message; what is trusted is the configuration it is checked against.
- Remaining lifetime: the adapter computes the expiry as the earlier of 15 minutes after the runner's readiness time and 15 minutes after the signed `Date` header, not from the message received time or the unverified token `exp` claim. A message whose signed `Date` is more than the configured clock-skew tolerance, initially 60 seconds, before readiness fails preflight. Within the tolerance, a `Date` earlier than readiness makes `Date` plus 15 minutes the earlier bound, so the adapter uses it. The reject rule removes a late message from an earlier attempt, whose `Date` is far before this readiness. The 60-second tolerance bounds expected clock skew between the runner and the signing server. The adapter enforces a configured minimum remaining lifetime, initially 10 minutes, sufficient for bounded login and identity validation, and a configured preflight deadline, initially 5 minutes, measured from the runner's readiness time. The minimum-remaining-lifetime check is independent of the tolerance and is measured at retrieval; an in-tolerance message read late in the preflight window that leaves less than the minimum still fails preflight.
- Identity and profile: from trusted configuration, with recipient binding established by the signed `To` check above, not by the delivery mailbox alone. The authentication mode is verified only after redemption, from application-derived evidence.

Separate the pre-redemption checks from post-redemption verification of actual session mode and identity. At app revision `fde9444416d7b4479a15337946170fec3ff4d507`, the [impersonation sign-in branch](https://github.com/foxglove/app/blob/fde9444416d7b4479a15337946170fec3ff4d507/packages/api/src/routes/v1/signin/index.ts) emits `CookieName.IMPERSONATE=1` in its response, and that branch is taken only for a token carrying an impersonator claim; `/v1/me` does not expose session source, and the internal session response's authority field is insufficient. A candidate adapter captures the actual approved-host sign-in response from the fresh browser and verifies its correlation to that browser's established session. A later mutable cookie-jar value or UI label is insufficient. Qualify ordinary and impersonation branches, a deliberately mislabelled message, missing/ambiguous evidence and full response capture; do not infer ordinary mode merely from an absent marker. If this cannot distinguish the modes reliably, an app-owned session-bound source signal is a release dependency. Retain only redacted validation results, never raw credential-bearing responses. The adapter emits `PREFLIGHT_PASSED` after successful mode and starting-identity verification. It emits `PREFLIGHT_FAILED` after any failure or when the configured preflight deadline expires. The failure result includes the existing classification, such as `EDGE_CONTROL_BLOCKED`, `ACCESS_FAILURE_UNCLASSIFIED`, or an application login failure. Gate attack tools until `PREFLIGHT_PASSED`; the harness prompt alone cannot enforce this boundary.

Mailbox APIs (for example Gmail `gmail.readonly` or Microsoft Graph `Mail.Read`) grant read access to a whole mailbox, not to one message, so per-message scoping is not a testable control. The testable controls are: the mailbox is dedicated to the test identity and is used for no other purpose; the runner has read-only access to that one mailbox and to no other mailbox; and single-use and 15-minute expiry are the accepted mitigation for earlier messages. Deny sending, deleting messages, and mailbox administration, including inherited grants: the runner must have neither an unrestricted parent credential nor permission to acquire one. Keep issuer, mailbox-administration, and read-only mailbox credentials inaccessible through the harness environment, mounts and metadata network path. The read-only mailbox credential is a long-lived login credential for the test identity, so the runner controller holds it outside the harness, and the issuer owner rotates and revokes it.

There is no stored login-handoff object, so there is no issuer-owned cleanup, no per-attempt cleanup record, and no cleanup-failure destination to select. The ordinary magic link is single-use with a 15-minute expiry enforced by the application; a redeemed link is inert and an unredeemed link expires without action. Mailbox-message retention is ordinary mailbox hygiene owned by the app/auth code owners; it does not change the evidence-retention policy. Qualify application single-use redemption, including concurrent attempts; deleting a message is not session revocation.

Verify I-01 and I-18–I-22 using actual workload identities and mailbox access as well as fixtures. No employee account, personal SSO cookie, or manual link is part of recurring bootstrap. Exercise employee-removal independence with isolated test fixtures rather than disabling a real person's account.

### Assessment operation

Before enabling live runs, record the responsible operator, the Monday 09:00 America/Los_Angeles scheduling mechanism including daylight-saving behavior, and the stop procedure. Manual runs have the same coverage requirement. Scheduling alone does not establish that an engineer is available; use an explicit operator coverage record and skip with a visible reason when absent (I-08).

Use the existing infrastructure GCS bucket module as a starting point, setting private-access options explicitly rather than relying on its provider defaults. Project/bucket, reader membership, workload identity and narrow write scope are implementation configuration; provision them through the owning infrastructure process as a separate dependency. Verify anonymous and unauthorized authenticated read denial as well as authorized read, no storage identity exposure to the harness, no credential/chain leakage into public workflow output, and the fail-closed behavior of an unavailable sink (I-15). Configure lifecycle expiry and effective version/soft-delete handling, preserve durable reconciliation state separately, and test expired references (I-17). No storage resource is provisioned by these docs.

Inspect the actual party edge controls and runner egress before selecting an access mechanism. If needed and supported, the environment owner supplies a narrowly scoped assessment-traffic policy; record its scope, owner and revision without changing production or the whole zone. Treat any exception as a qualification on coverage of the normal deployed edge. Prove reachability using the same browser/client/network path the harness will use. Cloudflare challenge detection can use `cf-mitigated: challenge`; other denials need corroborating edge evidence, and unclassified failures must remain unknown. Surface phase, affected coverage and observed challenge/block/unclassified counts in the private report, and test blocking both before authentication and after a valid positive (I-16). Unresolved edge access is a visible run failure and never a clean result. No live Cloudflare rule is changed by these docs.

Sonnet-4-8 records the operator's initial selection, not comparative cost/quality evidence. Qualify the selected exact provider/harness combination before release (I-12). Terra or Grok can be configured if independently supported; a name alone is not a usable model identifier, and the adapter may not silently replace the chosen model.

## Concurrent delivery

A retry after an uncertain write and two independent runs racing to create the same exploit ticket are different cases. Choose a coordination mechanism before integration, such as serialized reconciliation or durable identity/event coordination. Preserve one ticket per exploit while counting each independently confirmed run once. A failed reopen must not be recovered by creating a replacement ticket.

Add a controlled concurrent-run test once the mechanism is defined: two runs identify the same new exploit, or both contradict a fix claim, while one delivery loses its acknowledgment. Verify ticket uniqueness, per-run counts, correct final lifecycle, and honest summaries. The current I-06 retry criterion does not by itself prove concurrent behavior. The concrete concurrency mechanism and additional test remain engineering work; no claim of verification is implied.

## Failed stages and bounded reporting

A complete reconciliation failure bypasses delivery and records no new ticket writes. Preserve available redacted evidence and report the failed stage. Persisting that failure summary does not make the workflow successful. Per-finding invalid inputs remain independent when the rest of the input is usable.

Choose an explicit report retry limit, reserve reporting time within the total job budget, and stop retries at that limit or the job deadline. Reporting then terminates visibly as failed or timed out, with a redacted stage diagnostic when execution permits. Do not promise a later recovery worker. Retrying a report must not repeat ticket mutations; recovery requires original run/event identities and evidence that actually survived. Verify these paths with I-13 and I-14, including the distinction between a missing artifact and a persisted failure summary.
